# ADR 0001：技术栈选型

- 状态：已接受
- 日期：2026-11-23
- 决策人：开发方（待委托方确认）

## 背景

规划 §3.1 给出初步建议并允许论证替代。需要一次性定下：应用框架、UI 层、存储、ZIP、测试、质量门禁。约束有三条：

1. 移动端竖屏优先，输入响应要跟手；
2. 要能被第三方接手维护，不能选太小众的方案；
3. 内核产物必须与产品代码物理分离（GPL 义务边界）。

## 决策

| 领域 | 选择 | 版本 |
|---|---|---|
| 语言 | TypeScript（strict 全开） | 5.9.3 |
| 构建 | Vite | 8.3.8 |
| UI | React | 19.3.1 |
| 单元 / 集成测试 | Vitest + jsdom | 5.1.1 / 31.0.1 |
| E2E | Playwright Test | 1.65.1 |
| 静态检查 | ESLint + typescript-eslint | 10.15.0 / 8.73.0 |
| 存储 | IndexedDB（封装在 `src/saves/`，不外泄） | — |
| ZIP | 待 F14 前选定，要求：许可清晰、能流式处理、拒绝路径穿越 | — |
| 包管理 | npm（`package-lock.json` 入库） | 10.x |

## 理由

**React 而非原生组件。** 游戏库要做导入、列表、搜索、筛选、最近游玩、详情页，这些是典型的状态驱动列表 UI。原生组件省下的运行时开销，相比 J2ME 内核本身的占用可以忽略 —— 性能瓶颈在 wasm 与 canvas，不在 UI 层。选框架换来的是可维护性与团队接手成本。

**Vite 而非自建构建。** 需要代码分割（内核产物体积远大于应用代码）与快速的 HMR，自建没有收益。

**TypeScript strict + `noUncheckedIndexedAccess` + `exactOptionalPropertyTypes`。** 运行时适配层的状态机与事件载荷容易写错，这些开关能在编译期挡住大部分。代价是写起来啰嗦，值得。

**npm 而非 pnpm。** pnpm 更快、更省磁盘，但严格的 node_modules 结构会让部分工具（尤其跨包类型解析）出问题；本项目依赖量不大，收益不足以承担这个风险。锁文件入库保证可复现。

**存储用 IndexedDB 而非 localStorage。** 存档可能达到 MB 级，localStorage 有 5MB 硬限制且同步阻塞主线程。

## 后果

- 分发包会包含 React 运行时（当前约 71 KB gzip）。可接受。
- `tsconfig` 的严格选项会让初期的类型噪音变多，需要约定不滥用 `as` 与 `!`。
- ZIP 库尚未选定 —— 这是**已知缺口**，必须在 F14 开始前完成选型并登记到 `SOURCES.md`。

## 未采纳的方案

| 方案 | 未采纳原因 |
|---|---|
| 原生组件（无框架） | 列表与状态管理手写成本高，长期维护负担大于收益 |
| Vue | 与 React 能力相当，团队熟悉度优先 |
| Svelte | 生态与招聘面相对小，第三方接手成本高 |
| 整体打包（内核进 bundle） | 会让 GPL 义务边界模糊，见 ADR 0002 |
