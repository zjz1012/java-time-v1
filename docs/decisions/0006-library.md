# ADR 0006：游戏库与内置资产

- 状态：**已采纳**
- 日期：2026-11-24
- 相关：ADR 0005（存档按指纹隔离）、`docs/provenance/SOURCES.md` §5、F17

## 背景

V1.0 需要一个库页：列出游戏、搜、筛、点开就玩、能导入自己的 JAR。
随包要带 104 款（自研 6 + MIT 98，来源见 `SOURCE_AUDIT.md` §4.2）。

约束：
1. 静态站点，没有后端，也不能假设有 Node 进程。
2. 不引第三方依赖（此前已定的纪律）。
3. 存档按「JAR 字节的 SHA-256」隔离，所以库里的每个条目都必须知道自己
   的指纹 —— 否则启不启得起来都两说。

## 决策

### 1. 清单是生成物，指纹在生成时算

`src/library/catalog.ts` 由 `scripts/import-games.mjs` 生成，逐款**重算**
SHA-256 并写进清单，同时把 `.data` 与封面复制到 `public/games/`。

**为什么不引用旧 Toy 的 `manifest.json` 当运行时数据**：
- 那份清单里没有指纹，运行时补算意味着库页要 fetch 104 个包再算摘要
  （约 2.5 MB 读进内存 + 104 次哈希），首屏等不起；
- 里面的 `locked` 字段是 Toy 的「关注作者解锁」运营机制，与本站无关。

**为什么不在清单里写文件路径**：`/games/<id>.data` 是确定的，路径由 id
推导（`jarPath()` / `shotPath()`）。104 条各存两份路径等于把同一份信息存
两遍，改规则时得改 208 处。

★ 指纹在这里有第二个用途：**校验文件没被换过**。运行页 fetch 之后重算一遍，
与清单不符就拒绝启动 —— 否则游戏会带着「新内容的指纹」去读「旧版本存的档」。
生成与校验用同一份来源，两边不一致时错的是部署，不是游戏。

### 2. 路由用 hash，不用 path

`#/` 是库页，`#/play/<id>` 是运行页。

静态站点用 path 路由，刷新或分享链接时服务器找不到对应文件（404），得靠
`404.html` 重写兜底。hash 永远只请求 `index.html`，也不需要配置 base path。

同时保留 `?jar=<url>` 作为开发通道：它让「内核能不能跑」脱离游戏库可复现，
e2e 与排查内核问题都用它。它不写游玩记录 —— 那不是库里的条目。

### 3. 搜索是子串匹配 + 空格分词（AND），不做拼音

「空格分隔的每个词都必须命中」比「命中任一」更符合搜索直觉：输入
`贪吃蛇 方向键` 是在缩小范围，不是在扩大。

不做拼音/模糊匹配：那要带一张几万字的表，还会把 `san guo` 匹配到「三个蘑菇」
这类无关结果上。中文用户输入的是字，`搜不到` 比 `搜出一堆` 更容易理解。

### 4. 「最近玩过」是横条，不是排序

如果做成「玩过的排前面」，首屏会被七八款老游戏长期占住，找新游戏反而要先
滚过它们。改成独立一条横条（最多 6 个），主网格保持清单顺序。

记录里可能留着已删除游戏的 id（导入的包被删了），展示时跳过 ——
一条悬空记录不该让整条横条空掉。

### 5. 导入只做「是不是 ZIP」与指纹，不解析类结构

内核自己会做类解析并给出可读的失败，这里再验一遍只会多一套错误码，
而且两套判断标准迟早会不一致。

**唯一的例外是 `META-INF/MANIFEST.MF`**：读它只为拿 `MIDlet-Name` 当标题。
用户导入 `sokoban.jar`，卡片上写「sokoban」很怪 —— 包里的真名是「推箱子」。
这件事限制在「读一个条目」，任何一步不合预期（无 EOCD、非 STORE/DEFLATE、
解压失败、没有该字段）都退回文件名，绝不打断导入。

★ 解压用 `DecompressionStream('deflate-raw')`，数据经 `ReadableStream` 手工
喂入而不是 `new Blob([...]).stream()`：jsdom 的 `Blob` 没有 `stream()`，
后者会让这个功能在测试环境里静默降级，测了个寂寞。

### 6. 导入的游戏存 IndexedDB，元数据与字节分开两个 store

- `games`：id、标题、作者、大小、指纹、导入时间
- `blobs`：按 id 存 ArrayBuffer
- `plays`：游玩记录

分两个 store 不是为了整洁：列表页读 `games`，如果字节和元数据在同一个
store，`getAll()` 会把所有导入包的字节一起读进内存 —— 用户导了十个 16 MB
的包，光是打开库页就要占 160 MB。写完两个 store 在**同一个事务**里，
避免「有元数据没字节」的中间态（列表里看得见、点进去读不到）。

### 7. 导入游戏的 id 是 `user-` + 指纹前 16 位

同一个包再导入一次得到同样的 id，天然去重；不同包几乎不可能撞。

真的撞了（同 id 不同指纹）就**拒绝导入**并提示改名，不覆盖：覆盖会让
一款游戏的「最近游玩」挂到另一款头上，而这个错误在界面上完全看不出来。

## 被否决的做法

| 做法 | 为什么不 |
|---|---|
| 运行时 fetch 旧 Toy 的 `manifest.json` | 没有指纹；带 Toy 的 `locked` 运营字段；多一次请求与一套失败路径 |
| 库页显示前逐款算指纹 | 104 次 fetch + 哈希，首屏等不起，还会白耗 2.5 MB 流量 |
| 用 path 路由 + 404 重写 | 静态托管平台的重写规则各不相同，换平台就坏 |
| 拼音搜索 | 要带词典；结果里塞进无关游戏比搜不到更烦 |
| 把「最近玩过」做成排序 | 首屏被老游戏占住，新游戏要滚过去才找得到 |
| 导入时解析 `MIDlet-1` 类名去猜分类 | 类名与玩法没有可靠映射，猜错比「未分类」更糟 |
| 导入的字节与元数据放同一个 store | `getAll()` 会把所有包读进内存 |
| 存档直接按 id 隔离（而不是指纹） | id 可以被改（改名、重导），指纹不会；见 ADR 0005 决策 5 |

## 如何验证

- 清单与资产：`npm run check:games` 逐款重算 sha256 并核对数量（CI 每次跑）；
  单测另断言「指纹唯一」——重复即两款游戏共用存档，且不会报错。
- 纯逻辑：路由往返、坏 hash 回库页、搜索 AND 语义、分类与搜索叠加、
  最近玩过的排序与悬空记录、仓储的覆盖/去重/累加。
- 导入边界：空文件、超上限（不读进内存）、非 ZIP、截断的 ZIP、损坏的中央目录、
  同 id 不同指纹。
- manifest：deflate / STORE / 带注释的 EOCD / 小写路径 / 续行 / 缺字段。
- 真浏览器：库页 104 张卡、点开出画、退出回库并进「最近玩过」、搜索与筛选、
  直接开 `#/play/<id>`、未知 id 的提示页。
