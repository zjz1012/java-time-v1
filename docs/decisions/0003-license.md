# ADR 0003：自有代码采用 GPL-2.0-or-later

- 状态：已接受（取代 2026-11-23 的 `GPL-3.0-only` 初版）
- 日期：2026-11-23（初版同日修订）
- 相关：`docs/provenance/CORE_EVALUATION.md` §5、ADR 0002

## 背景

仓库要公开，必须为「本项目自己的代码」定一个许可。此前 README 写的是「待委托方确认」，
这种状态下第三方连 fork 的合法依据都没有，等于挂了空许可。

更硬的约束来自内核：PluotSorbet 的 `LICENSE` 是 GPL-2.0 正文，**无 "or later" 字样**，
即 **GPL-2.0-only**。FSF 的立场是 GPLv2-only 与 GPLv3 不兼容 —— 若二者构成**单一结合作品**，
则无法同时满足两份许可。

初版曾选 `GPL-3.0-only`，理由是「与委托方另一个工程的许可一致」。该决策带来一个直接后果：
在组合方式未定之前，**不得对外分发「本仓库代码 + 内核」的组合产物**，等于把发版卡住。
本次修订即为了解决这一点。

## 决策

本仓库自有代码采用 **GPL-2.0-or-later**：

- 根目录 `LICENSE` 为 GPL-2.0 全文（339 行，md5 `b234ee4d69f5fce4486a80fdaf4a4263`），
  与仓库内已登记的 `docs/provenance/license-texts/GPL-2.0.txt` **同一份字节**，
  避免出现两份措辞不同的 GPL-2.0 原文（gnu.org 现行版本把 FSF 地址改成了 URL，
  法律文本主体一致，但不必引入第二个变体）。
- `package.json` 的 `license` 字段写 `GPL-2.0-or-later`（SPDX 标识）。
- 授权声明文本按 FSF 推荐措辞：*"This program is free software; you can redistribute it
  and/or modify it under the terms of the GNU General Public License as published by the
  Free Software Foundation; either version 2 of the License, or (at your option) any later
  version."*

## 为什么是 or-later，而不是 only

三个候选的差别只在两处：能不能和 v2-only 的内核一起发，以及将来能不能往上走。

| 维度 | GPL-3.0-only | GPL-2.0-only | GPL-2.0-or-later |
|---|---|---|---|
| 与内核 v2-only 组合分发 | 不兼容 | 合法 | 合法（整体选 v2） |
| 将来整体升到 v3 | 已锁死 | 锁死 | 下游可自行选 v3 |
| 专利授权条款 | 有 | 无 | 可选 v3 取得 |
| 与 Apache-2.0 代码合并 | 兼容 | 不兼容 | 同左，可选 v3 |
| GPLv3 §3 反规避条款 | 有（潜在摩擦） | 无 | 无（除非下游选 v3） |

`-only` 是单向门：只要还用这个内核，就永久放弃上表中 v3 的三项好处，且不能引入任何
GPL-3.0 代码。`or-later` 则保住了两条路 —— 现在按 v2 组合分发合规，将来若换内核或
整体重授权，许可证文本本身就允许走到 v3。

初版 ADR 否掉 `or-later` 的理由是「本项目没有让别人用 GPLv4 的实际需求」，这个理由搞反了：
**or-later 的价值不在「让别人用 v4」，而在「自己日后能整体升 v3」**。对一个内核可能被替换、
仍在迭代的项目，这恰恰是需要保留的余地。

代价只有一个：v2 是 1991 年的文本，FSF 自己认为它在专利与 tivoization 上有缺陷。
本项目无专利、无硬件锁定场景，这两项缺陷落不到实处；而 `or-later` 已把「日后取得 v3 条款」
的路径留开。

## 后果：组合分发限制解除

原 ADR 末尾那条「方案未定之前不得分发组合产物」的封锁**解除**。现在：

1. 「本仓库代码 + 内核产物」可以作为一个整体分发，整体按 **GPLv2** 提供；
2. 分发时须同时提供：GPL-2.0 全文、本仓库完整源码、内核对应的完整源码
   （含对上游的修改，获取方式须在应用内可见）；
3. 因为内核是 v2-only，这个组合作品**不能**整体按 v3 分发 —— 这是内核带来的天花板，
   不是本仓库选择的结果。

## 这个决定不解决的问题

**1. 3D 那条路没有变。**

`CORE_EVALUATION.md` §5.2 说「补回 3D 须引入 freej2me（GPL-3.0），冲突会立即回归」，
这句话在 `or-later` 下**依然成立**：内核把组合作品锁在 v2，GPL-3.0 代码进不来。
B1（3D 做不做）只能靠「把 3D 模块隔离为独立程序」或「换内核」解决，不能靠换许可解决。

**2. 隔离执行仍然值得做，但理由从合规降级为工程。**

iframe 的动机里，许可只是第五条。前四条换许可也去不掉：内核要求 13 个 DOM 节点
（Worker 没有 DOM）、`config` 是 `var` 全局会污染宿主动作用域、`load()` 走写死相对路径、
内核崩溃会带走整个页面。换许可后的变化是：iframe 从**合规必需**变成**工程更优**，
某些部署形态下若不便用 iframe，不再因此触雷。见 ADR 0002。

## 影响

- 任何人 fork 本仓库，可按 GPLv2 或（自行选择）GPLv3 及以上版本使用与再分发。
- 由于是 Web 前端产物，源码天然可见，但仍须保留 `LICENSE` 与
  `docs/provenance/` 下的第三方声明。
- 随包的 92 款 MIT 游戏与本仓库形成的是「聚合」而非衍生关系（独立 JAR，由内核加载），
  不受本决策影响，仅须保留其原版权声明。
