# ADR 0003：自有代码采用 GPL-3.0-only

- 状态：已接受（组合问题部分为待决，见末节）
- 日期：2026-11-23
- 相关：`docs/provenance/CORE_EVALUATION.md` §5、ADR 0002

## 背景

仓库要公开，必须为「本项目自己的代码」定一个许可。此前 README 写的是「待委托方确认」，
这种状态下第三方连 fork 的合法依据都没有，等于挂了空许可。

候选与约束：

| 候选 | 问题 |
|---|---|
| MIT | 只覆盖自有部分，但整体产物仍受内核 GPL-2.0 约束。容易被读者误读成「整个产物都是 MIT」，实际不成立 |
| GPL-2.0-or-later | 与内核 GPL-2.0-only 组合时最省事（可整体按 v2 分发）。但与既有事实不符：委托方的另一个 Toy 已是 GPL-3.0 |
| **GPL-3.0-only** | 与委托方既有工程的许可一致；GPLv3 的专利授权与反规避条款更完整 |

## 决策

本仓库自有代码采用 **GPL-3.0-only**：

- 根目录 `LICENSE` 为 gnu.org 的 GPL-3.0 全文（674 行，md5 `1ebbd3e34237af26da5dc08a4e440464`）。
- `package.json` 的 `license` 字段写 `GPL-3.0-only`（SPDX 标识，明确「不再授权更高版本」）。
- README「许可与来源」一节改为三分：自有代码 / 内核 / 随包游戏，各自许可不同，不再混为一句。

## 为什么选 only 而不是 or-later

`or-later` 允许下游改用未来版本，看似更宽松，但本项目没有「让别人用 GPLv4」的实际需求；
反过来，`only` 让许可边界确定，便于将来若要与 GPL-2.0-only 内核做组合判断时，
至少自己这一侧没有额外变量。

## 待决：与内核 GPL-2.0-only 的组合

这是 B2（分发形态）的一部分，此处只记录事实与候选方案，**未做结论**。

事实：

1. 内核 PluotSorbet 的 `LICENSE` 是 GPL-2.0 正文，**无 "or later" 字样**。
2. 本仓库自有代码是 GPL-3.0-only。
3. FSF 的立场是 GPLv2-only 与 GPLv3 不兼容 —— 若二者构成**单一结合作品**，则无法同时满足两份许可。
4. 当前实现把内核挡在仓库之外（`public/kernel/` 在 `.gitignore` 里），
   所以**本仓库本身**是纯 GPL-3.0 代码，不涉及组合。

候选方案（择一，或组合）：

| 方案 | 做法 | 代价 |
|---|---|---|
| A. 维持分离执行 | 内核跑在独立 origin / Worker，与本仓库代码只通过 `postMessage` 通信，主张「独立程序、非结合作品」 | 需改 ADR 0002 的加载方式；跨 origin 增加部署复杂度 |
| B. 自有代码改 GPL-2.0-or-later | 单一结合作品整体按 GPLv2 分发 | 与委托方既有工程许可不一致；需重新决策 |
| C. 加链接例外 | 作为版权人，在自有代码上追加「允许与 GPL-2.0-only 代码组合并按 GPLv2 分发」的附加许可 | 非标准做法，需逐条写清，且下游理解成本高 |
| D. 换内核 | 换成宽松许可的 J2ME 实现 | 目前无成熟方案，CheerpJ 为商业授权 |

**在方案未定之前，不得对外分发「本仓库代码 + 内核」的组合产物**；仓库公开本身不受影响，
因为仓库里没有内核。

## 影响

- 任何人 fork 本仓库都要遵守 GPL-3.0：衍生作品同样以 GPL-3.0 分发，并提供完整对应源码。
- 由于是 Web 前端产物，源码天然可见，但仍须保留 `LICENSE` 与
  `docs/provenance/` 下的第三方声明。
- 随包的 98 款 MIT 游戏与本仓库形成的是「聚合」而非衍生关系（独立 JAR，由内核加载），
  不受本决策影响，仅须保留其原版权声明。
